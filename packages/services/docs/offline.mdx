# Offline & sync

`@oxy.so/services` is offline-first out of the box. Its data lives in `@oxy.so/bloom-data`: every read is held in the signed-in account's store and copied to disk, every write shows at once and waits for the network when there is none, and the UI knows when the network goes down. Nothing here is opt-in — wiring up `OxyProvider` lights up all of it.

## Each account's store

The session opens one bloom-data store per account, on every account change and before anything is woken (`data/accountData.ts`):

| | |
|---|---|
| Durable copy | one SQLite file per account on a device (`expo-sqlite`), one IndexedDB database on the web, memory where neither exists |
| Signed out | a store of its own (`SIGNED_OUT_DATA_ACCOUNT`), so public reads never reach an account's |
| Account switch | the next account's store opens; an answer that lands for the account that was left is dropped. Nothing is wiped by hand |
| Sign-out | the account's store and its file are deleted (`clearAllAccountData()` does the same on demand) |

A screen reads the disk copy as it opens and then the network when the copy is stale, so held data renders on first paint without a global restore. The SDK's reads keep their staleness, their gating (`skip`) and one retry rule (`data/readOptions.ts`).

An app keeps its own per-account data the same way: entities, lists and sources of its own in the store `useStore()` returns (or `currentStore()` outside React). See bloom-data's documentation.

## Writes

Every write hook (`useUpdateProfile`, `useLogoutSession`, …) is a bloom-data action and returns an `ActionView` (`run`, `isPending`, `error`, `data`, `reset`). A write shows at once as an optimistic layer; when the server answers, its answer replaces the layer, and when it fails, exactly that layer is dropped. Offline, the write waits for the network (counted as `paused`) and runs when it is back; if the account is left meanwhile, it is dropped.

## Reading sync status

```tsx
import { useMutationStatus } from '@oxy.so/services';

function SyncPill() {
  const { isSyncing, isOffline } = useMutationStatus();
  if (!isSyncing) return null;
  return <Pill tone="neutral">{isOffline ? 'Waiting for network' : 'Syncing'}</Pill>;
}
```

`useMutationStatus()` reports the signed-in account's writes: `pending` (running), `paused` (waiting for the network), `total`, `isOffline` and `isSyncing`.

## Reading online state

```tsx
import { useOnlineStatus } from '@oxy.so/services';

function OfflineBanner() {
  const online = useOnlineStatus();
  if (online) return null;
  return (
    <View>
      <Text>Offline — changes will sync when you're back online.</Text>
    </View>
  );
}
```

`useOnlineStatus()` reads bloom-data's `environment` through `useSyncExternalStore` — no `useEffect`, no polling. `OxyProvider` reports NetInfo (online) and AppState (in front) to it on native; on web it listens to the browser itself.

## Device key-value data

What the SDK keeps for the device rather than an account (the language, the cached boot, campaign attribution) is a model in the device's own bloom-data store behind the same `StorageInterface`. It moves off AsyncStorage (localStorage on the web) read-through: the first read of a key copies its old value and deletes the old key, so only the SDK's keys move and an app's own keys are never touched. The SDK's dead keys (the session ids it wrote and never read, and the 14.x React Query caches `oxy_query_cache_v3` and `oxy_account_queries:<account>`) are deleted once.

## What about the HTTP cache?

`@oxy.so/core`'s `HttpService` also keeps a short-lived in-memory cache keyed by `GET:<path>`. Mutations call `clearCacheByPrefix(...)` for the affected prefixes so the next read pulls fresh data. If you write custom endpoints, follow the same pattern:

```ts
await oxy.users.updateProfile(input);
oxy.http.clearCacheByPrefix('GET:/my-custom-endpoint/');
```

## File uploads on RN

On React Native (Expo 56), uploads route through `XMLHttpRequest` rather than `fetch` because Expo's `fetch` rejects RN file descriptors for multipart bodies. `useUploadFile` and `useUploadAvatar` already handle this — call them and you get progress events for free.

## Listening to session events

`useSessionSocket()` subscribes to remote session events with zero config:

```tsx
function SessionGuard() {
  useSessionSocket();
  return null;
}
```

Only three events ever trigger a local sign-out: `session_removed`, `device_removed`, `sessions_removed`. Unknown events log a dev warning and do nothing — there is no fallback `else` branch that would force the app offline.
