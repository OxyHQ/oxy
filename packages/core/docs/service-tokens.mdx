# Service tokens

A service token is a short-lived Ed25519-signed JWT that says which
application a backend is. `OxyServer` mints, caches and refreshes it; you never
handle it. What differs is how the backend proves who it is:

| Who | Proof | Authority | Configure |
|---|---|---|---|
| **An Oxy-owned backend** (Mention, Peable, Alia, …) | Workload attestation: the infrastructure it runs on (the ECS task role) vouches for it ([ADR 0026](../../../docs/adr/0026-first-party-services-authenticate-as-workloads.md), [ADR 0049](../../../docs/adr/0049-first-party-platform-authority.md)) | `first_party`, no scope list | Nothing — no key, no secret |
| **A third-party customer backend** | An `ApplicationCredential` key pair (client id + secret) | `external`, the credential's scopes | `serviceAuth: { apiKey, apiSecret }` |

**An Oxy-owned backend never holds an api key, a client secret or an
`OXY_API_KEY`, never POSTs to `/auth/service-token` by hand, and never keeps a
credential "as a fallback" beside its workload.** An official application name
does not promote a customer key either: a key is always `external`.

## Oxy's own backends

One `OxyServer` per process, exported from one module:

```ts
import { OxyServer } from '@oxy.so/core/server';

export const oxy = new OxyServer({
  baseURL: process.env.OXY_API_URL ?? 'https://api.oxy.so',
  applicationId: process.env.OXY_APPLICATION_ID,
  serviceIdentity: 'when-anonymous',
});
```

- On ECS the token comes from the task role; nothing else is configured. To
  attest from a developer's AWS SSO profile as well, pass
  `workloadCredentials: createAwsWorkloadCredentialProvider()` from
  `@oxy.so/core/server/aws`.
- `serviceIdentity: 'when-anonymous'` sends every request that has no user
  session — `users.get`, `users.lookupMany`, profile reads — with the service
  token instead of anonymous. Oxy charges anonymous traffic to the source
  address, which a whole fleet shares behind one NAT; Mention measured
  543–575 ms anonymous against 19–24 ms with the token.
- `applicationId` names this backend's application, for its
  [application roles](./application-roles.mdx).

### Calling another Oxy product

Use that product's SDK (`peableForOxyService({ oxy })`, …) or a service client
on the same `OxyServer`, with the receiving application's audience:

```ts
const product = oxy.createServiceClient({
  baseURL: 'https://<product-api-origin>',
  audience: 'oxy-service:<receiving application id>',
});
const response = await product.fetch('/v1/things', { method: 'POST', body });
// Keep the client for the life of the process; dispose() it on shutdown.
```

Kaana's audience is `'kaana.ai'`. Never build a second `OxyServer` for this,
and never keep a second token cache.

## Third-party customer backends

A developer's own backend authenticates with a credential of its application
(`type: 'service'`, created in the Oxy Console). The `publicKey` (`oxy_dk_…`) is
a public client id; the secret is shown once at creation and rotation.

```ts
const oxy = new OxyServer({
  baseURL: 'https://api.oxy.so',
  serviceAuth: { apiKey: process.env.OXY_CLIENT_ID, apiSecret: process.env.OXY_CLIENT_SECRET },
});
```

The token carries the credential's scopes, capped by the application's
ceiling; `oxy.middleware.requireScope(scope)` enforces them on a receiver.
Rotation keeps the previous secret valid for 24 hours. Keep the secret in a
secret manager, never in client code or a committed file.

## Acting for a person

Three different things; pick by what you hold:

- **The person is in the request** (their bearer reached your backend through
  `middleware.auth()`): call Oxy as them with
  `oxy.withUser(req, (user) => user.accounts.get(id))`. See
  [building a backend](./backend.mdx#as-the-person-behind-the-request).
- **Your service acts with the person's proof** (a forwarded session, a task,
  a capability ticket): `oxy.withRequester({ requesterToken | taskId | capabilityTicket })`,
  or `createServiceClient({ requester })`. Durable work keeps the `taskId`
  from `oxy.agency.createTask(…)`, never the bearer.
- **No person present** (a long import): ask Oxy whether they may, with your
  own token — `oxy.accounts.accessFor(accountId, userId)`:

```ts
const verdict = await oxy.accounts.accessFor(channelId, userId);
// { accountId, kind: 'channel', access: { role, permissions, status: 'active', source } | null }
if (verdict.kind !== 'channel' || !verdict.access) throw new Error('Not a member of that channel');
```

`access` is `null` for no active membership and for an archived, unknown or
unclaimed directory account. The answer is never cached, and anything but a
valid verdict throws, so a caller fails closed. Gate on `access.permissions`,
never on `access.role`.

Never trust a caller-supplied user id header, and never persist a bearer.

## Protecting your own endpoints

`oxy.middleware.service()` admits service tokens only; `oxy.middleware.auth()`
admits users and services alike. An Oxy-owned receiver names its own
audience — once, on the server:

```ts
const oxy = new OxyServer({
  baseURL: 'https://api.oxy.so',
  applicationId: OWN_APP_ID,
  serviceIdentity: 'when-anonymous',
  expectedAudience: `oxy-service:${OWN_APP_ID}`,
});

app.use('/internal', oxy.middleware.service());
app.post('/internal/replay-webhook', (req, res) => {
  // req.serviceApp: the calling application, with authority 'first_party' or 'external'.
  res.json({ replayed: true });
});
```

A first-party token is checked against Oxy's live introspection on every
request, so a revoked binding stops working at once; an external token carries
its scopes (`oxy.middleware.requireScope('files:read')`). Verification uses the
Oxy JWKS at `https://api.oxy.so/.well-known/jwks.json`; a token whose header is
anything but `{ "alg": "EdDSA", "typ": "JWT", "kid": … }` is refused before a
key is looked up, and an unknown `kid` refreshes the key set at most once a
minute.

## What a service token cannot do

- Act as a person for a human-facing action. Use the person's own session
  (`withUser`) or their requester proof (`withRequester`).
- Hold an application's operator powers: `appPermissionsFor` and
  `requireAppPermission` refuse service-token requests.
- Skip rate limits: it is charged to its own application instead of an IP.
