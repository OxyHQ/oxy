Original status: design from source inspection and limited existing reproductions; no production implementation or completed compatibility proof. The observations and exact reproductions are in [the audit](2026-10-31-session-socket-actor-audit.md). This proposal does not assert authorization from decoded JWT claims, cancel an already-sent request, or guarantee that a client immediately knows about a remote change.

## Problem and consistency boundary

For an account-mode client, a new authoritative snapshot may name the same subject with a different human actor. The flat device state identifies only the subject (`activeAccountId`) and may contain multiple sessions for it; the directory identifies a context and actor; the bearer authenticates a session. A coherent snapshot must identify the same device-row incarnation, device revision, active context, actor, subject and session that the bearer was minted for. "Same subject" and "same revision number" alone are not enough.

Scope is a locally committed, holder-proven account-mode snapshot at a server-validated point in time. Account graph/profile data may change without device revision: `reconcileContexts` deliberately materializes or prunes unused rows without bumping it. A directory containing all profiles and availability verdicts is therefore not, by itself, a single transactionally frozen authorization snapshot. Revalidation cannot exclude a subsequent transition after the final server read. The UI must not claim the current remote actor has not changed since the client last synchronized.

## Server: candidate separately versioned holder endpoint

Do not add tokens to `GET /session/device/state` or `GET /session/device/directory`: `packages/api/src/routes/sessionDevice.ts` deliberately returns `activeToken: null` on the bearer-authenticated state endpoint because knowing a bearer for one account does not prove entitlement to every other account's token. Existing bearer-only endpoints and the `deviceTokenMintResponseSchema` remain byte-compatible. A separate negotiated `POST /session/device/context-sync` (name provisional) could require the same `{deviceId, deviceSecret}` holder proof, rate limiting, request validation and cache/secret handling as the existing `/token` endpoint. It must not perform `/activate` or alter the active context.

For unpinned account mode, the proposed success response would include a version discriminator and the holder-proven device-row incarnation ID (or another server-issued per-incarnation value), monotonic device revision, `activeContextId`, the context's actor ID, subject ID and exact active session ID, plus the flat state, directory projection, access token/expiry and unchanged `nextDeviceSecret`. These identifiers are consistency data, not proof of authorization. The server itself must resolve the active context and session, validate the session and its delegation, and bind the returned bearer to that server-resolved pair. It must not choose a session by first matching `accountId`. An empty/superseded/unauthorized/credential-lost outcome needs an explicit typed response with no bearer; client policy must distinguish transient errors, 429, revoked holder and truly empty state without clearing credentials on ambiguous errors.

Feasibility work in `packages/api/src/services/deviceSession.service.ts` should use its `getStateBySecret`, `resolveActiveToken`, `load`/`loadDevice`, `getDirectory`/`buildDirectory` and the revision/context revalidation pattern of #2038. Capture the internal row ID, credential identity, revision, context, actor, subject and session; after mint and directory projection revalidate the same row, holder and binding before returning. A targeted PostgreSQL test must validate concurrent activation, revocation, and row replacement before accepting the claim. Optimistic revalidation is a candidate, not a claim of full serializability. `getDirectory` can reconcile in its own transaction and session minting uses pooled DB work; holding the device row lock around existing nested calls can deadlock or fail to protect external session/permission changes. Redesign that work or prove the chosen isolation; never assume that simply wrapping existing calls in a transaction is sufficient.

A versioned schema belongs in both `packages/contracts/src/deviceSession.ts` and its zero-Zod `packages/contracts/src/client/deviceSession.ts`, with parity tests and stable client exports; the endpoint belongs beside `/token` in `packages/api/src/routes/sessionDevice.ts`, with contract, authorization, rate-limit, secret redaction and DB concurrency tests. The token payload may be decoded as an additional local consistency check, never used instead of the server's authorization. Avoid logging the bearer, holder secret or identifying response values.

For identity-pinned mode, do not reuse an active-device-context token to follow another actor. Preserve the existing explicit `accountId` mint, local key proof and refusal in `resolveTokenForAccount` when more than one context matches. Design an identity-bound version independently if a complete binding is needed; do not assume actor == pinned subject or that every pinned identity is a personal account without a contract. OAuth-isolated sessions and external access-token providers are outside this device-holder protocol.

## Client: shared transition barrier

A server response alone does not make client observations atomic. `SessionClient.applyState` and `fetchDirectory` mutate fields before notifying; `getState`, `getDirectory` and `getActiveContext` expose them synchronously; `HttpService.setTokens` synchronously invokes token listeners; `createOxyRuntime.reconcileFromClient` separately projects data. A listener can re-enter getters or send a request between those operations.

An opt-in strict capability would require one per-OxyServices transition owner shared by `SessionClient`, `HttpService` and `OxyRuntime`, not a React-only memo or effect:

1. As soon as an accepted higher-revision device signal or a conflicting directory is observed, synchronously advance an ownership generation and close a shared private-action gate before exposing any new half. Existing action closures check the live generation and gate before starting. A request that has already left the process is outside this guarantee.
2. Fetch a holder-proven versioned snapshot, staging it outside all public state. Refetch/coalesce via the existing device-secret single flight without accepting a mint started before the new ownership generation as proof. One bounded new attempt may be needed after a superseded flight; keep existing 429/backoff limits.
3. Verify the server-returned device incarnation, context, actor, session and revision against the locally observed high-water mark and ownership generation. CAS-protect durable credential persistence. Carry the exact server-returned active session ID into persistence and runtime; never use `accounts.find(accountId)` to choose between actors. If the binding changes, token is absent, a holder changes, or the result is unsupported/unknown, remain explicitly unavailable and retain recoverable data. Do not silently downgrade strict behavior on transient failures.
4. Install token and staged facts under one logical commit with re-entrant getters/action checks guarded throughout; only then publish notifications and open the gate. This likely requires a staged/transactional token install API in `packages/core/src/HttpService.ts` or an equivalent shared controller; merely suppressing React rerenders is insufficient. Audit provider synchronization, `skipAuth`, explicit Authorization overrides and unmounted/captured callbacks before choosing its scope. Do not expose a raw secret through snapshots.
5. Route socket handling, `refreshDirectory`, token refresh, activation, bootstrap, sign-out and direct read paths through the same ownership boundary. The relevant code spans `packages/core/src/session/SessionClient.ts`, `packages/core/src/session/refresh.ts`, `packages/core/src/HttpService.ts`, `packages/core/src/session/sessionClientHost.ts`, `packages/services/src/ui/session/tokenTransport.ts`, `packages/services/src/ui/runtime/createOxyRuntime.ts` and `packages/services/src/ui/context/OxyContext.tsx`. Retain `session_accounts_changed` as a wake-up, not authority.

Because older servers and externally managed/opaque tokens cannot establish this binding through today's interfaces, strict behavior must be explicitly opt-in with an observable `unknown`/`unavailable` state until a capability is established. A legacy app and non-strict behavior must continue to work as before. Capability detection must not treat a timeout, 5xx, unrecognized malformed response or network attacker as evidence permitting fallback; use an explicit supported/unsupported version response. Pin, OAuth-isolated and managed external providers need separate compatibility proofs rather than being forced into this account-mode protocol.

## Proof required before implementation can be considered complete

- Server tests with real PostgreSQL, actual session mint and holder proof: two actors under one subject, token and binding from the same context, concurrent A→B→A before/during/after mint and directory read, equal-revision idempotence, revoked/replaced holder, device row deletion/recreation, changed session binding, delegation revoked, no-token, no accidental new device, and no leaked bearer on denial. Cover that revision does not freeze the account graph.
- Full client/provider tests using the actual HTTP route and real token emitter, not a fabricated `/state` bearer: socket signals in both orders, dropped second signal, direct `refreshDirectory`, `getState`/`getDirectory` reads before notifications, and synchronous `setTokens` listeners that invoke a retained action. Check action/request behavior before and during commit and response/body handling for work already sent.
- Concurrent old/new snapshots and refreshes with same account and same/different session IDs, same-session refresh and holder rotation, logout and A→B→A; stale single-flight completion; credential CAS failure; storage or network failure; 429 cooldown; recovery without clearing unrelated state; device incarnation changes.
- Compatibility for old server explicit unsupported response, opaque/legacy JWTs, unknown external providers, unpinned clients that have never loaded a directory, identity pin personal/foreign/same-subject/ambiguous, OAuth isolation, cold boot, refresh and ordinary sign-in. Check strict unavailable UX and non-strict unchanged behavior.
- API/schema parity, TypeScript, tests against the actual published Core/Services tarballs, native/web behavior, and independent security review. These are future requirements, not checks performed in this design exercise.

No implementation cut is currently demonstrated to cover both socket and direct directory refresh while preserving synchronous getter/request semantics, identity pinning and legacy compatibility. A documentation-only contract and the earlier reproducible evidence are safe incremental artifacts; forcing a refresh only in the socket handler or only delaying notifications is not.

One further compatibility boundary: `bindSessionToContext` is currently best-effort and documents that a valid login may temporarily lack device/context claims until a later re-mint. A strict v2 endpoint cannot interpret a missing binding as an authorization failure or silently invent it. It needs an explicit recoverable `binding_unavailable` outcome, a separately verified means to establish/revalidate the binding, and regression tests for first login, remint, session replacement and concurrent logout. Existing sign-in behavior must remain unchanged until that recovery is proven.
