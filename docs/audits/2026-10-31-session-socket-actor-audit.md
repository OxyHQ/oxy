## Reproduction and scope

On `origin/main` at `29ff6016d`, with a real PostgreSQL fixture, the real device-directory service and real JWT signer, two people have distinct live delegated sessions for the same organization. Alice is active and a SessionClient holds Alice's bearer. Activating Bob changes the active context but retains the same subject organization.

The isolated test was in `packages/api/src/services/__tests__/deviceDirectory.service.test.ts` on an unmerged branch, test name `audit real mint with same-subject`. It uses the real SessionClient and Services token transport, while dispatch of socket events and HTTP transport are controlled fixtures. No real network socket or complete OxyRuntimeProvider tree is involved. The pre-existing ephemeral database harness creates and disposes its own test database. It ran against a disposable local PostgreSQL through the repository's ephemeral test-database harness (`packages/api/src/db/testDatabase.ts`, `TEST_DATABASE_URL`) with a dedicated Jest config, `--runInBand`, filtered by test name.

Both cases currently pass as observations of the existing behavior. After the `session_state` event, a real client subscriber sees Bob in the directory while its bearer still has Alice's actor. The same-subject token transport does not refresh. The socket handler also skips its own bootstrap because the subject matches the projected account. The test supplies a **synthetic** `/session/device/state` response containing a newly minted token, so its later convergence assertion does not represent the real route. On the real route, `GET /session/device/state` returns `withoutActiveToken(...)`, i.e. `activeToken: null`, deliberately: bearer authentication proves the device, not entitlement to another account's bearer. A separate lightweight client reproduction uses Core 7.10.1 SessionClient and Services token transport with synthetic socket/JWT and a literal `{state, activeToken: null}` GET fixture. After both signals it observes actor Bob with Alice's bearer, two state reads and zero refreshes. It exercises the literal route response contract, not the actual HTTP router, backend authorization, or real tokens. The script was `packages/services/src/ui/session/actor-null-signal.audit.ts` on the same unmerged branch. The activation route emits both signals (device room first, user room second), and the subscriber mismatch already occurs after the first signal. The signal is a wake-up, not an authorization decision.

A separate test, `audit explicit directory refresh after another actor activates the same subject`, uses the same real database and issuer and proves that `refreshDirectory()` alone also publishes the new actor with the previous bearer; it does not inject a socket event. A socket-handler-only fix therefore cannot cover that path.

The second socket test supplies an artificial identity pin equal to the organization. It demonstrates that the synthetic bearer-bearing bootstrap can plant a same-subject bearer with a different actor in that configuration; the actual GET route does not supply that bearer. It does **not** establish that an organization pin is reachable or permitted in a real identity provider. Existing identity contracts and tests explicitly preserve pinned behavior when the active subject is different; they also allow a same-subject sync token. Do not infer actor equality with subject or change that contract without demonstrating the valid identity modes.

## Constraints on a shared fix

The flat device state has no unique active context identifier; the same organization can occur under multiple principals. Comparing only `activeAccountId`, or picking a matching flat account, cannot prove actor identity. The directory names the active context, and the JWT can include `device_context_id` and actor claims, but clients also support legacy/opaque bearers with absent claims. These fields are consistency evidence, not authorization.

Delaying listener notifications alone is insufficient: `applyState` updates the state read by `getState()` synchronously and `fetchDirectory` updates the value returned by `getDirectory()` before notify. `refreshDirectory`, signal-driven bootstrap, socket events, explicit activation, removal and sign-in can overlap. Any implementation that claims coherent public snapshots must stage state, directory and the associated bearer until an authoritative response is validated; track device/lifecycle and highest observed revision; reject stale or inconsistent outcomes; and only commit the coherent result once. It must also cover direct getters and retained callbacks, not just render notifications. Requests already sent cannot be undone.

An account-mode-only experiment may treat a same-subject push as a wake-up and obtain an authoritative state and bearer before advancing its public snapshot, retaining the previous coherent snapshot or exposing an explicit unavailable state when verification or re-mint fails. The existing `/state` route intentionally returns no bearer. A fix must use a properly proven device-secret mint or a newly designed authenticated binding protocol, and must not add bearer disclosure to the existing bearer-authenticated GET. The current transport short-circuits a same-subject bearer and swallows refresh failures, so its present API does not prove successful reconciliation. It must not silently follow an opaque provider's changes or treat a decoded claim as authority. Full server/client guarantees still depend on binding response and token to the same device revision and context; the server PR #2038 and Core PR #2039 each have separately documented limits.

Before proposing a fix, tests should cover real service + issuer and concurrent A→B→A, state GET and directory GET resolving in both orders, response without bearer, an unrelated higher revision, device replacement, stale socket callbacks, failures/recovery, account mode with known and absent claims, and identity-pinned personal/foreign/same-subject cases. Keep the existing behavior for unknown and legacy claims unless a separately reviewed contract justifies a stricter opt-in. Also test two providers and distinguish events delivered by actual socket rooms from fixture-injected events.

## Additional contract findings (static review)

The real `GET /session/device/state` intentionally returns `activeToken: null`. Its bearer proves the device and does not authorize disclosing another account's token. Do not change that GET into a token dispenser. The existing secret-proven `POST /session/device/token` mints for the current active context in account mode without activating it again; identity mode instead passes the pinned account explicitly. `resolveActiveToken` checks revision and active context around the mint, but a response does not carry `activeContextId`, and the separately read directory may race or be from a recreated row. The result gives no universal actor binding for legacy/opaque tokens.

A further **untested hypothesis**: the server's flat projection emits an entry per context, so two entries can share an `accountId`. `refreshDeviceSecretArm` selects the first matching account to persist a `sessionId`, and `activeSessionIdOf` similarly selects the first for the runtime projection. The first entry may not correspond to the current actor. The ordering and user-visible effect need a real fixture before attributing a bug; this is not evidence that every mint has a wrong session.

A candidate protocol for strict account mode would return a server-vouched device-instance generation, revision, active context, state, directory and bearer together in a secret-proven response, with an explicit stale/no-token outcome if the binding cannot be established. Its compatibility, database consistency and behavior after the final server read require proof. For an old server or a token/provider that cannot supply the necessary binding, strict consumers must receive an explicit unknown/unavailable verdict; existing non-strict behavior remains a separate compatibility policy. Existing externally supplied access-token providers cannot be assumed synchronous or observable.

The client side cannot make a single atomic guarantee merely by calling `setTokens` and then assigning directory: `HttpService.setTokens` invokes token listeners synchronously, and those listeners may re-enter public getters or start requests before the second assignment. A real barrier must be shared by token installation, public snapshots and action/request entry, with transition ownership advanced before any re-entrant observer and notifications released only after commit. This does not cancel requests already sent or prevent a remote change before the client learns about it. Identity-pinned clients need a separate contract in which their own identity bearer does not follow the device's globally active context; the global directory is descriptive and may legitimately differ from that bearer. No implementation is proposed until these boundaries, legacy behavior, same-subject refreshes and concurrent/re-entrant transitions are proven.

`resolveTokenForAccount` explicitly returns null if more than one session/context matches a pinned `accountId`. Thus the synthetic organization-pin/two-actor case does not establish that the real pinned mint succeeds: the actual mint fails closed for ambiguity. Any new protocol must preserve that refusal and the pinned identity's own recovery contract.
