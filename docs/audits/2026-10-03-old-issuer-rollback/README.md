# Old issuer against schema 142: local rollback rehearsal

This rehearsal demonstrates compatibility of ordinary authentication and a **required maintenance stop**, not an unconditional production rollback. No AWS, production database, provider, email, or device operation ran. The old issuer cannot safely accept traffic carrying the new agent provenance until the affected pending authorizations and sessions have been stopped and all old processes start cold. Independently running receivers and financial workers require their own stop.

## Rollback admission gate (proposed production procedure, not executed here)

Root accepted the following as a maintenance contingency. The operator must capture the actual service, task definition, desired count, routes/targets, and receiver inventory before applying it. No new public kill flag is assumed.

1. **Stop new work outside the issuer first.** Identify and pause agent/requester coordinators, persistent MCP receivers, metered spending, subscription awards/refunds and provider feed writers that can use cached or offline JWT authority. Record each concrete service/worker, its stop mechanism, active-request drain and readback. The issuer stop below does not stop another service's offline token acceptance. Keep provider delivery retry/queue retention intact; never acknowledge an unprocessed event as successful.
2. **Quiesce the issuer.** Capture its previous `desiredCount`, then scale that exact ECS service to zero. Require `runningCount=0`, `pendingCount=0`, every task from its captured set `STOPPED`, and every relevant ALB target drained/no healthy target. Check all ingress paths, including any direct/internal path. Non-effectful probes of password/token/ticket admission must fail unavailable rather than return an accepted response. A503 is the expected maintenance HTTP result; any successful admission or unaccounted route blocks continuation. This rehearsal did not execute ECS or these probes against production.
3. **Inventory while admission is closed.** Capture exact IDs, row `xmin`, owner/operator, status and expiry for `sessions` with non-null `auth_method_id`, `auth_codes` with non-null `auth_method_id`, and OAuth `auth_sessions` whose `approved_by_session_id` references one of those sessions. Preserve method/owner/provenance fields. Record counts and a digest of the target set; independently account for any agent-derived session issued during a previously exposed old-runtime window, because such a session may have null provenance.
4. **Stop the exact authorization set.** Under reviewed transactional locks/CAS, expire still-pending codes and agent-approved pending/authorized OAuth requests, then deactivate affected live sessions using the canonical final service semantics. Retain rows and tombstones; do not delete keys/identities, clear provenance, touch unrelated ordinary sessions, or disable database constraints. Verify every selected ID and unchanged provenance after the operation, and reject a changed target set. The pending-approval stop is a required follow-up operational control; only code expiry and canonical session deactivation were executed in this rehearsal. No ready-to-run production CAS writer is supplied here.
5. **Start old cold, with new lanes still closed.** Select the captured TD692 image digest, start fresh processes only, and restore the captured desired count after the stop receipts are complete. No warmed old process or session cache may survive. Probe ordinary personal/device/app-only flows plus rejection of the stopped agent sessions/codes before admitting ordinary traffic. The local cold control demonstrates why this order matters. Do not resume unsupported requester/self or financial behavior merely because ordinary auth works.
6. **Preserve schema/history.** Leave schema142 and all additive rows in place. No down migration. Restoring final code later does not justify automatically reviving stopped authorizations; reauthorization follows the normal current protocol. Reconcile queued provider work before resuming each independently paused writer.

The source has `INFERENCE_EDGE_AUDIENCE=closed` for inference admission and `startProviderCostFeedSchedule()` in API bootstrap. These are source observations, not verified production stop receipts. Retiring all final issuer tasks also retires their embedded schedules. No universal flag for all billing/webhook/offline receiver effects was established. A rollback remains blocked until the separate receiver/worker inventory and controls above are concrete and reviewed. In old67c09, `server.ts` bootstrap itself starts auto-recharge (around1197), reservation expiry (around1222), reconciliation (around1324), background jobs (1380) and subscription expiry (1410). Scaling to zero stops them only while the service is stopped; restarting the unmodified production entrypoint restarts them. Step5 therefore cannot be treated as a financial-lane-closed production start until those embedded writers have an independently implemented and verified stop strategy. This harness bypasses that bootstrap and ran no ticks. It proves auth compatibility, not that such a production stop strategy already exists.

## Historical evidence and limits

`proof.json` hashes the executed harness, exact product trees, built dependency trees and records. Historical private logs remain hashed with their outcome; no fixture tokens, signing keys, database payloads or login material are copied into this audit.

Earlier fixture failures are retained honestly: an incorrect token response field, JSON instead of OAuth form encoding, a missing Redis close that required stopping the exact own probe process, and an incorrect expectation that omitting a caller catalog pin would reject despite a pinned durable approval. These are setup/assertion errors, not product failures. The warm-old200 after canonical deactivation and the provenance-dropping old exchange are actual observed product incompatibilities. The final full matrix was rerun against the final product composition after those fixture corrections.

The prior [schema142 migration proof](../2026-10-03-i05-foreground-approval-p2/proof.json) separately covers upgrading141 with historical requester rows, retained IDs/creation/run history, and denied reactivation. Its exact migration/test source hashes were checked here; that historical upgrade was reused, not rerun. This invocation did run fresh142 and repeat with count142 after both.

This audit does not authorize or claim an executed production rollback, full API suite, container-image equivalence, new provider effects, all-worker compatibility, or native/web acceptance. Those remain separate evidence.
