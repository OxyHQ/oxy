# One temporary Mercaria development credential

This internal operator procedure implements the approved I08 sandbox namespace preparation for existing application `6a37d0cc5d4b5f15482a9340`, owned by account `69b2d3df5d12f58c9800d651`. It does not create a customer identity, offer, price, merchant terms, user consent, grant, workload binding, Stripe key, or persistent SSM secret. It does not activate a production payment cohort.

The preceding [application/credential CAS](../1519-mercaria-billing-authority/README.md) must have added only `payments:read` and `payments:write` to the reviewed existing six-scope ceiling. This operation creates at most one usable development **service** credential for that application, with precisely those two scopes and an absolute lifetime no longer than one hour from the prepared intent. Its `createdByUserId` is null; the authenticated operator is attributed in a private STS receipt, not impersonated as a customer. Existing production credentials remain unchanged.

`machine` is not interchangeable: the canonical schema gives machine credentials no secret hash, and the existing service-token route requires `type=service`. This helper reuses canonical material generation (24 random public-key bytes, 32 secret bytes, SHA-256 verifier), `isCredentialUsable`, owner/closure checks, and PostgreSQL locking. It adds no schema or public route.

## Authority and transaction

Prepare takes owner SHARE then application UPDATE locks, verifies owner active/no closure fence, first-party active application, exact approved scope ceiling, and no usable development service credential. The returned plan fixes credential UUID, nonce, absolute expiry and application `xmin`/timestamp/scopes. Issue repeats those checks under the same lock order, validates the application CAS, rechecks expiry after waiting, and inserts one row. Competing helper issuances serialize through the application lock. The helper does not claim a new global uniqueness constraint for other credential issuers.

Inspect and revoke identify the original row by UUID, application, nonce-derived name, public key, hash, type, development namespace, two exact scopes, expiry, null creator/rotation/workload. Revoke also checks fresh `xmin`/timestamp/status under row lock, changes only status and timestamp, and reads back `revoked`. Revocation remains possible after owner closure; a new issue does not. No row is deleted. A mint updates `lastUsedAt` and therefore `xmin`: cleanup must take a fresh inspect result, not reuse the issue receipt. A concurrent update after inspect causes a refusal requiring investigation, not a blind retry.

## Lost responses, cleanup and token limits

If issue's ACK is lost, retain the same original plan, UUID/nonce and material. Reconcile using inspect; never create another intent automatically. The private `registered.json` and RunTask clientToken/startedBy allow reconciliation after an uncertain AWS response. If a task ARN was not returned, root must reconcile it before further operations; automatic cleanup cannot claim an unknown task was stopped. An empty reserved result file is not success.

Task cleanup is independent of DB credential cleanup: known owned tasks are stopped/read back and the temporary definition deregistered/read back, including after receipt loss. Failure to stop does not skip deregistration; failures remain explicit. Deregistration does not stop a running task. Root resolves residual tasks and revokes the exact credential separately. The launcher does not retry arbitrary mutations or claim cleanup based solely on an API ACK.

Expiry/revocation makes `isCredentialUsable` reject the **next mint**. Actual HTTP tests observe successful mint then elapsed expiry401, and mint then exact CAS revocation401. A JWT already signed retains its signature and `exp` (current issuer TTL300 seconds). This procedure does not assert immediate invalidation at Peable or other receivers, and does not change their caches or revocation policy. Observe the actual issuer TTL and receiver behavior during the operation; conservatively allow the full already-issued TTL after last mint/revocation before claiming the bearer window drained. No production latency or instantaneous revocation guarantee follows from local fixtures.
