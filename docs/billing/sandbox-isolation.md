# Physically isolated billing sandbox

Billing sandbox is a separate API process and a separate, newly provisioned database. It never shares `user_credits`, customer references, subscriptions, product sources, events or authority with the live database. Credit balances remain one aggregate per account within that database; this change does not reinterpret or partition existing balances.

The supported provider pairs are `live / production`, or `test / test`, `test / staging`, and `test / development`. A test Stripe key requires an explicit `BILLING_PROCESSOR_ENVIRONMENT` and `NODE_ENV=test` or `development`. A production process cannot use a test key, even when an environment override names a sandbox. With no Stripe key, the existing live/production deployment remains the default; provider calls still require a key.

A sandbox database must be explicitly provisioned with the database-wide setting `oxy.billing_namespace=test:<environment>`. Provisioning uses `ALTER DATABASE` only on a freshly created, verified, empty sandbox database. No runtime code declares or converts an existing database. An unmarked database is the live boundary. A marked sandbox rejects live configuration, and a test process rejects an unmarked database or a different sandbox declaration.

The guard reads only the selected `oxy.billing_namespace` value from `pg_db_role_setting`, for the current database and `setrole=0`. Session settings, role-specific settings, connection options and `PGOPTIONS` cannot declare this boundary. Connecting validates the declaration before publishing the DB handle; `getDb` also rejects a changed runtime configuration. Financial/product helpers and every Stripe operation revalidate the persisted declaration. Helpers accepting a transaction check that transaction's database. Product authority reads and lifecycle/cancellation select the configured namespace; product DB constraints accept only the supported pairs.

Treat the declaration as immutable provisioning metadata throughout the process lifetime. This is a deployment boundary, not protection against a malicious DBA or direct privileged SQL. Do not repurpose a populated database by changing its declaration, and do not share live application credentials or authority stores with a sandbox.

Provider catalogue price bindings and explicit historical subscription mappings include account, mode and environment. The same provider account can legitimately have separate test/live price identities; selection never falls back across those namespaces. Existing explicit subscription configuration must include its mode/environment; missing fields fail closed. No prices, Oxy One composition, promotions or conversion from provider costs to credits are inferred.

The local API fixture provisions a new migrated sandbox database, keeps all successful Stripe evidence `livemode=false`, and runs the real HTTP/SQL billing, lifecycle, ledger and cancellation paths. A deliberately contradictory delivery is rejected; successful evidence is never rewritten to live. Separate normal/sandbox DB fixtures prove that the same account ID can have a sandbox balance while its normal balance remains unchanged, and that a misconfigured process fails before provider access, balance mutation or authority reads. All provider calls in these fixtures are synthetic. A real Stripe sandbox cycle still requires its separately reviewed bounded script and recorded provider evidence; these fixtures do not claim it.

Migration `0140_billing_sandbox_namespace` changes only two access CHECK constraints. It does not declare any database as sandbox, seed a catalogue or enable production checkout. The normal migrator remains the only DDL apply path. The owned local rehearsal verifies its fresh Postgres PID, executable, data directory and socket before provisioning, applies all migrations and repeats them as a no-op, then stops the server.
