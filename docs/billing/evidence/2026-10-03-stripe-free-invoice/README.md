# Authenticated free-invoice boundary and local recovery

The reviewed zero-only plan used one owned zero-price subscription and no paid budget. The provider returned its paid-zero invoice and event. The original runner then failed its HTTP200 assertion: its catalogue incorrectly placed price0 in a binding that requires a positive paid amount. All seven returned objects were cleaned/read back, no creation intent remains unresolved, and both owned PostgreSQL and child stopped. The original failed receipt stays intact and requires manifest review. This was a free-price case, not proof of a 100% discount on a paid price.

A bounded authenticated read-only GET recovered the same actual invoice/event. A fresh owned, persistently marked test:test database reinstates the original fixture payer ID and Stripe customer. Through the actual raw-body receiver and locally generated valid signature, the original catalogue reproduces500 and a failed receipt with its positive-amount validation error. With the valid paid catalogue containing no mapping for that free price, the same event returns200; replay returns200. SQL confirms one receipt (`not_granted`, attempts3), zero credit/access grants, zero financial transactions and zero balance. External requests are denied in this local fixture; no provider mutation occurs. The provider's public webhook delivery is not tested.

The correction belongs to the runner: it excludes free prices from the paid mapping and validates configuration before writing it. Product schema/runtime and the HTTP200 assertion stay intact. Refusals now record a whitelisted HTTP status/code without arbitrary response text. Twelve plan/diagnostic tests, scripts TypeScript and scoped Biome pass. The first local harness run incorrectly queried `detail` instead of `outcome_detail`; that failure is retained separately and is not a product defect.

Run the local replay with `python3 scripts/billing/test-stripe-zero-receiver.py <owned-private-run-directory>`.
