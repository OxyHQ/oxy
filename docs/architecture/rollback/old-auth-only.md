# Old-derived AUTH-only variant: proposed implementation scope

Base67c09 corresponds to the immutable old TD692, but this variant will be a new image. It is not production-ready. The exact mode/admission/module-load/startup census is in old-auth-only-proposed-scope.json. No production effects have run.

Use one explicit OXY_RUNTIME_MODE with normal as the existing default and rollback-auth-only as the sole new mode. Invalid configuration must abort startup rather than fall back. Admit only enumerated method/path pairs before parsers and Inbox mounting, with the existing origin, body validation, authentication and rate-limit middleware still applied afterward. Both direct and one-prefix /api routes obey the same allowlist. OPTIONS requires the exact requested method/path. Unknown routes, product mutations, provider webhooks, capability/requester/MCP and inference return503 before their handlers. HTTP body streaming must not get through an earlier mount. Do not expose a new dynamic listener or delegate to an inline partial app.

Workload and service-token endpoints remain app-only and retain exact existing scope/credential/attestation/replay checks; that does not authorize a stopped independent receiver to resume unsupported work. Foreground/new OAuth authorization and code exchange stay closed. A useful ordinary rollback retains key/password/TOTP/email sign-in, canonical device binding/switch/signout, validation/logout and users.me. Auth email delivery is an intentional request effect; disabling autonomous email outboxes is not a claim that all authentication is side-effect-free. All retired agent/lost-provenance sessions/codes require the final CAS and cold-start control before admission. The selected key challenge/verify handlers require their own bot/person distinction review against the captured authority set.

The first server import currently initializes real-time, Socket.IO, platform activity/infrastructure and Redis broadcast machinery. Those must be detached/disabled before mode-specific bootstrap. OpenTelemetry can start exporters on import and will be disabled for this restricted mode. Startup still waits for PostgreSQL and reads the canonical active-origin snapshot, but skips redirect repair, policy seed and all listed business schedules/workers. Default normal takes the original path with unchanged policy and registration order.

Memory-only cleanup timers are a separate census, not financial writers: sessions/users/login lockout support auth; location/files/credential domains/performance/block/email caches come from otherwise-unused imports. The implementation must either avoid the unused imports or gate those cleanup registrations explicitly. Any retained auth-memory cleanup must be reported rather than described as zero process timers. No environment-driven replacement of timer globals is admissible in the production variant. Tests may instrument registration at controlled seams to observe which real functions ran, while SQL/network controls establish the effects that did not occur.

Acceptance needs real production bootstrap invoked locally against additive schema142, module-load/worker-registration census, a normal-mode control, ordinary key/password/device/app-only cold flows, and rejection of retired agent/code authority. Non-auth routes and realtime/socket bypasses must fail before effects; high-signal fixtures should use provider/billing rows so equality is meaningful. Finally a built immutable image must pass startup/admission controls and independent source/lock/security inspection. Keeping the fleet in maintenance until forward repair is currently safe but cannot be presented as restored old authentication. This source census does not yet fulfill the useful rollback criterion.

The exact `POST /accounts/:accountId/switch` remains available for an ordinary principal with current `act_as` membership. Admission rejects every `X-Oxy-User-Id` header before parsers, including service-token requests. The restricted session boundary rereads both account and operator in SQL and rejects bot subjects or bot operators, including managed organization sessions and device token mint. It does not reactivate agent authority or create standing delegation.


## Candidate image delivery

The existing candidate-only ARM workflow permits exactly the dedicated branch and paths for this variant. Its token stays `contents: read`; it builds the real Dockerfile with `--load`, inspects all materialized Forge copies, and uploads its image/config/build metadata and regression results. It does not use AWS credentials or push a registry image. This first stage supplies image/source inspection, not a production fallback.

The immutable image must subsequently execute the same compiled bootstrap/admission controls against an owned additive schema142 database, with `OXY_RUNTIME_MODE=rollback-auth-only` explicitly pinned. The container digest, exact task mode and tested runtime configuration belong together: default normal deliberately remains normal, so this image without that mode is not a safe fallback. An ARM image source/config proof alone does not establish a runnable authentication fallback.

New runtime bytes require their own source/input-tree and image binding. Neither the issuer-only policy nor the final release policy is transferred to this branch. The dedicated security gate and provenance must be reviewed before any registry promotion. No ECR push, task update or deployment is performed by this workflow or local rehearsal. This branch never modifies the final integration freeze. Until the image/transport proof exists, the operational contingency remains maintenance503; TD692 in its ordinary mode is not a safe financial rollback.
