# Old issuer authorization retirement and maintenance boundary

This preparation addresses the observed old67c09/TD692 exchange of an agent authorization code with lost provenance and its warm session cache. It does not admit a production rollback. The immutable old image is `sha256:4512fc8d29abedf67caa2a77194e6fa351c38ebe2201e57bf320276e105da38a`.

## Exact SQL plan and phases

`packages/api/src/scripts/oldIssuerAuthRetirement.ts` has a default read-only `prepare` CLI. It captures a repeatable-read snapshot, bounded to 1000 rows per table, under a statement timeout. The reviewed input supplies the maintenance manifest SHA256, exact service/task-definition/task/target-group set, expected autoscaling presence, exact admission probe paths, and any independently established accidental-issuance session IDs. No selection by username, speculative time window, or bot-looking account is used to infer lost provenance.

The target includes all non-null agent-method sessions, all agent-method authorization codes, and OAuth approvals linked through `approved_by_session_id`. Explicitly reviewed provenance-lost sessions also include their approvals and the exact `finalized_auth_code_id`, even when that code has NULL method provenance. Independent unlinked codes from an old issuance window still require explicit investigation before rollback; this selector does not pretend to discover unknowable history. NULL provenance is preserved, never repaired by guesswork.

Each row carries its ID, `xmin`, owner/operator, immutable relationship fields and a SQL SHA256 of its full authority row. Raw session tokens, refresh tokens, code hashes and claim secrets never leave SQL through this snapshot. The hash excludes only permitted retirement mutations: session `is_active` and the canonical method's `updated_at`, code expiry, and approval status/expiry. Every other authority change, including scopes, token rotation or a changed row census, rejects the operation. The snapshot and its SHA256 are pinned in a strict plan with a 30-minute maximum validity.

Before each effect the executor requires a fresh observer result, at most 60 seconds old, matching the manifest and every captured task and probe path. Every service must have desired/running/pending zero, all captured tasks STOPPED, each exact target group drained, no standalone writers, and external/internal admission probes503. Every previously registered autoscaling target must have all three suspension bits true; absence or drift is rejected. The plan preserves the original operational manifest for later restoration. The observer must perform real GETs and probes; a historical preflight or a callback returning stored JSON is not production evidence. This patch supplies strict validation and the SQL executor, not a production fleet-observation transport or a live execution command.

1. Fsync an authorization-expiry intent in the external operator journal, then reobserve quiescence.
2. In one SQL transaction lock sessions, codes and approvals in stable ID order, validate exact authority/census, expire unused/unexpired codes and pending/authorized OAuth approvals with parameterized ID+`xmin` predicates. A failure rolls back both expiry sets. Used/consumed history remains unchanged.
3. Persist expiry confirmation, then retire each still-active selected session through canonical `deactivateSession(sessionId, { expectedXmin })`. Its SQL predicate is atomic and a mismatch throws before a confirmation. Existing callers keep their old boolean behavior. Canonical cache invalidation still runs. Recheck quiescence after the last blocking journal/observer await and before each write.
4. Re-read the whole authority set and record completion only when codes/approvals are unusable and sessions inactive with provenance/history retained. Completion explicitly says maintenance is still required.

There is no global transaction across SQL phases and cache invalidation. A lost acknowledgment can resume with the same exact plan while it is valid: already expired rows and inactive sessions are recognized without reviving authority. Changed authority requires a new reviewed snapshot. If the plan expires after an effect, keep maintenance and prepare a fresh read-only plan from actual state; never extend expiry or revive the retired rows. This is preparation, not an executed fleet stop.

## Old production bootstrap: concrete writers

All references below are source67c09, not the test host. The old auth rehearsal deliberately did not call production bootstrap. Its table equality checks therefore cannot cover these ticks. Exact source hashes/comparisons are in the dated `old-writer-sources.json`.

The new per-grant credit/provider tables are not directly referenced by these old functions. That is not proof of safety: old `db/credits.ts` and billing routes differ and can alter the aggregate balance without the new grant-consumption/refund provenance. Request routes remain writers even if all timers are disabled.

## Minimal useful rollback strategy, not implemented

The immediately valid contingency is continued maintenance followed by forward repair. It safely preserves data but does not restore old authentication availability.

If restoring old ordinary authentication is necessary, prepare a separately reviewed immutable old-derived variant. Its source must explicitly prevent **all** autonomous bootstrap scheduling/worker startup and non-auth effect routes from being admitted, including financial webhooks, spending, inference, unsupported requester/agent capability lanes and catalogue/configuration writes. Gate the real startup and route registration in source; do not inject a runtime entrypoint or invent environment flags presumed to exist in TD692. Keep only the agreed ordinary authentication/device and necessary profile reads, with the same canonical parsers, middleware and session semantics. Separate audit/auth writes remain deliberate and testable.

The variant needs a concrete route/worker census, negative boot tests proving no timer/queue/provider side effect, real SQL ordinary-auth and stopped-agent/code controls after cold restart, and an independently inspected immutable image. Provider deliveries must stay retryable rather than be acknowledged without processing. Any non-auth route retained requires explicit compatibility proof for its writes. It is a new image, not TD692, and the security/source/image gate must be revalidated for that exact artifact. No variant is implemented or authorized as production-ready by this document. No service scaling, authority mutation, provider effect or deployment ran in this preparation.
